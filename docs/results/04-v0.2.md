# 04. Runtime v0.2: child process, cancel, priority, model pool, embeddings, LoRA, cold load

Measured on the owner's laptop on 22 Nov 2026, about 11:00 to 12:30 IST. i5-1135G7, 16 GB, Windows 11, llama.cpp CPU build 12248, runtime v0.2 (release build).
**The laptop was on battery** for all of these runs (47% → 40%, `bench\out\power.log` from 11:47 on). Absolute speeds may be lower than on AC; every comparison below was made within one session.
About 6 GB of RAM was free. Single runs unless a count is given. Scripts are in the session scratchpad unless named; the reusable ones are `runtime\scripts\smoke.ps1` and `bench\src\bin\nocachecopy.rs`.

## 1. Child-process mode

`--port 0 --parent-pid <pid> --port-file <file>`, parent = a `powershell Start-Sleep` process.

| Check | Result |
|---|---|
| stdout | exactly one line, `JITMO_RUNTIME_LISTENING port=62324`; the log went to stderr |
| `--port-file` | the same line, written before the first request could arrive |
| Parent killed | runtime noticed and exited **73 ms** later; the loaded llama-server child was gone; the port file was removed |

## 2. Warm-up

`POST /admin/load {"model":"router"}` (270M router, cold process, warm file cache): returned after the model was ready, `load_ms` 1076. A second call: `was_loaded: true`, 0 ms. Unknown model: 404.

## 3. Cancel and client disconnect

Qwen3.5-0.8B, a 1500-token non-stop request (`ignore_eos`). Checked in llama-server's log (`cancel task`, then `stop processing`) and by the child's CPU time.

| Case | Client got | llama-server | Child CPU over the next 3 s |
|---|---|---|---|
| `DELETE` a running non-stream request (after 3 s) | `499 request_cancelled` after 3.34 s, header `X-Jitmo-Request-Id: run-1` | `cancel task` | +0.016 s (idle) |
| `DELETE` a queued request (behind a running one) | `499` at once (1.32 s after it was sent, 0.1 s after the DELETE); the running one went on | – | – |
| `DELETE` a running stream | 102 SSE events, then `data: {"error":{"code":"request_cancelled",...}}` and `data: [DONE]` | `cancel task` | – |
| Client closes a stream (`curl -m 3`) | – | `cancel task` | +0.016 s |
| Client closes a non-stream request (`curl -m 3`) | – | `cancel task` | +0.0 s |
| `DELETE` an unknown id | `404 request_not_found` | – | – |

After all of these, `GET /v1/requests` was empty. **Closing the connection is enough to stop llama-server**, for streams and non-streamed requests (axum drops the handler, which drops the upstream request; llama-server notices the closed socket).

## 4. Priority

One `background` request running (200 tokens), then queued in this order: `bg-a` (background), `bg-b` (background), `ia-a` (interactive).
`/stats` showed `running 1, waiting 3 (2 background, 1 interactive)`. They finished in the order **running-bg, ia-a, bg-a, bg-b**: the interactive one jumped the queue, the running background one was not interrupted. A bad `X-Jitmo-Priority` value gives 400.

## 5. Chains with several inputs

Chain `qa`: step 1 on the 270M router (`Question: {question}`), step 2 on Qwen3.5-0.8B (`system = "Answer from this passage only: {passage}"`).

```json
{"vars": {"question": "Who built the lighthouse?", "passage": "The lighthouse on Kell Island was built by Mara Voss in 1871."},
 "system": {"answer": "Reply in at most 8 words. Passage: {passage}"}}
```

Output `Mara Voss.`; step 1 loaded the router on demand (911 ms). A run without `passage` was refused before any generation (400: `chain 'qa' needs the variable(s) ["passage"]`). The chat form (`model: "chain:qa"` plus top-level `vars`) answered `Ann built it.` The v0.1 form `{"input": "..."}` still works (unit tests and smoke test).

## 6. Model pool: switching

Alternating 8-token requests between jitmo agent's **Gemma 3 270M router fine-tune** and **Gemma 3n E2B**, 5 each, after one warm-up load of each (warm file cache). Wall time per request at the client; `load` = time this request waited for its model.

| Pool | Router request | Gemma 3n request | Loads during the 10 requests |
|---|---|---|---|
| **Both resident** (`pool_budget_mb = 0`; estimates 1201 + 2663 = 3864 MB, both fit with the default 1536 MB reserve) | median **166 ms** (111–177) | median **984 ms** (908–995) | 0 |
| **One at a time** (`pool_budget_mb = 3000`: every switch evicts the other) | median **1400 ms** (1331–1466), of which load 1174–1316 ms | median **2894 ms** (2827–2961), of which load 1789–2062 ms | 10 (one per request) |

- With both resident, a switch costs nothing measurable: each child keeps its own KV and prompt cache.
- An eviction plus reload costs about **1.2 s for the 270M model and 1.9 s for Gemma 3n**. Most of that is llama-server's own start (process, backend DLLs, weights mapping), not reading the file: the 241 MiB router file still takes 1.2 s.
- Memory with both loaded: router working set 329 MB (private 140), Gemma 3n 1572 MB (private 370).
- The same with Qwen3.5-0.8B + the router under a 2000 MB budget: reloads of 1.5–1.6 s and 1.0–1.1 s.

Pool rules, checked once each:

| Check | Result |
|---|---|
| A model that is generating is not evicted (`max_concurrent = 2`, Qwen3.5-0.8B generating, router requested, budget 2000) | `503 insufficient_memory: ... loaded and not evictable: qwen08 (1595 MB, in use)`; after the generation ended the router loaded (evicting it) |
| A pinned model is not evicted | `503 insufficient_memory: ... router (1201 MB, pinned)` |
| `/stats` per model | state, load estimate, working set, private, last use, loads, evictions |

## 8. LoRA

No published GGUF LoRA for our base models was found quickly, so a **synthetic adapter** was made: rank 1, on every `ffn_down` of the 270M router model (18 layers), random normal weights with std 0.3 (seed 0), alpha 1. Written with the `gguf` Python library by `benchmake_lora.py` (run with `V:jitmo-sandbox	rainenv`; `general.type = adapter`, `adapter.type = lora`), 196 KB: `V:\jitmo-sandbox\adapters\router-synthetic-r1.gguf`.
The weights are large on purpose, so that the adapter visibly changes the output and a scale switch can be seen.

Same prompt ("Name three colors."), temperature 0, 12 tokens, one router child, in this order:

| Request | Output |
|---|---|
| no `lora` | `Name three colors` (the base model's output) |
| scale 1 | `kyed Espcul EspLiبراير back Petrosuada` |
| scale 0.3 | `ric crestillsricricculric totalälälrikric` |
| scale 0 | `Name three colors` |
| (all four again) | the same four outputs (base once ended with a `.`, see below) |
| chain: step without `lora`, then step with `lora` (scale 1) | `Name three colors.` / `kyed Espcul ...` |

- llama-server loaded the adapter, and the **scale switches per request with no reload** (1 load for the whole test).
- **A bug was found and fixed:** in build 12248 a request that does not name an adapter gets it at its load-time scale 1.0, even with `--lora-init-without-apply`. The first run gave the scale-1 output for "no lora" and for a chain step without `lora`. The runtime now always sends the full list with scale 0 for unnamed adapters.
- The base output sometimes ends with a `.` and sometimes not (scale 0 vs no lora, and on the second round). Probably small numeric differences when the prompt comes from llama-server's prompt cache; not investigated.
- A trained adapter (real task, real quality) is still untested.

## 9. Cold load from the SSD

Emptying the Windows standby list needs admin rights, so each model file was **copied with `FILE_FLAG_NO_BUFFERING` on both sides** (`bench\src\bin\nocachecopy.rs`): neither the source nor the copy enters the file cache, so the copy's first read comes from the SSD. The copies were on the same drive (V:) under `runtime\target\coldtest\` and deleted afterwards.
Check of the method: reading a fresh copy with 16 MB reads took 2.34 s (1.07 GB/s, SSD), then 1.79 and 1.68 s (cached). So the copy was not cached.

Through the runtime: `POST /admin/load` on the fresh copy (cold), then unload, then load again (warm). `load` = start to ready; then one 16-token request.

| Model | Run | Load cold | Load warm | Cold − warm | First request cold / warm |
|---|---|---|---|---|---|
| Qwen3-4B (2.38 GiB, all of it is read) | 1 | 2878 ms | 2194 ms | +0.7 s | 2528 / 2466 ms |
| | 2 | 4164 ms | 3846 ms | +0.3 s | 2443 / 2420 ms |
| Gemma 3n E2B (2.82 GiB, PLE half not read) | 1 | 5444 ms | 6661 ms | −1.2 s | 2847 / 2894 ms |
| | 2 | 4393 ms | 3774 ms | +0.6 s | 1973 / 1961 ms |

- **A cold load costs about 0.3 to 0.7 s more** for these 2.4 to 2.8 GiB files on this SSD (about 1.1 to 1.9 GB/s). The first request after a cold load is not slower: the weights were read during the load.
- **Load time is noisy**: 2.2 to 6.7 s for the same file in the same hour (on battery, other apps open). The noise is larger than the cold penalty.
- Gemma 3n's working set after a cold load is the same 1571 MB as warm: its PLE table stays on disk either way.

## 10. Load-time RAM check (v0.1 fix)

The estimate is now `private (auto cap) + mapped file − tensors left on disk` (details in 06-runtime-api.md, "Load estimate"). Gemma 3n: 4103 → **2663 MB** (measured working set 1572 MB). With the default `reserve_free_mb = 1536` it loaded next to the router with 6 GB free; the v0.1 rule would have needed 5639 MB free for Gemma 3n alone.
